# Sistema Vira Real — MySQL como Banco e Entrega em Pasta com Atalho (Sem Instalador)

**Resumo**: depois do rascunho ser apresentado e 100% aprovado (ver linha do tempo 03/09/2026 e 04/09/2026 em [[Sistema de Relatório de Devoluções — Contexto e Objetivo Inicial]]), o projeto muda de fase — deixa de ser prova de conceito e passa a ser desenvolvido como sistema real. Duas decisões de arquitetura fecham essa virada: o banco de dados troca de SQLite pra MySQL (mesmo padrão do Sistema Interno V2), e o modelo de entrega do app fica definido como a pasta com o `.exe` dentro (`--onedir`, já validada), com um atalho do Windows apontando pra dentro dela — descartando tanto o `.exe` único quanto um instalador completo.

> [!success] Decidido — 04/09/2026, 20:26
> MySQL + MySQL Workbench como banco (config manual na 1ª vez, migrations automáticas depois via `launcher.py`), entrega em pasta (`--onedir`) com atalho no lugar de instalador. Regra fixada: usuária final nunca precisa do dev pra iniciar/manter o dia a dia — só abrir o atalho.

## Contexto

Com o rascunho validado por quem realmente vai usar (colega de equipe, usuária final) e pelo superior do usuário, o projeto deixou de ser um experimento descartável — ver linha do tempo em [[Sistema de Relatório de Devoluções — Contexto e Objetivo Inicial]] (04/09/2026, 20:00). Isso reabriu 2 decisões que tinham sido fechadas ainda no começo do projeto, sob premissas que não valem mais: o banco de dados (SQLite foi escolhido em 01/09/2026 pra evitar a complexidade de instalar/gerenciar MySQL) e o modelo de entrega (só tinha sido validado o `.exe` em pasta, nunca comparado de propósito contra alternativas).

## O problema

Definir, com o projeto agora tratado como sistema real (não mais rascunho): (1) qual banco de dados usar, e como ele se conecta ao app entregue como `.exe`; e (2) qual o melhor formato de entrega do app pra usuária final, entre 3 opções levantadas pelo usuário — `.exe` único, pasta com `.exe` dentro, ou instalador com atalho gerado.

## O que levou à resposta

Banco de dados: o usuário deixou claro que não quer "sofrer" reinventando solução nova — quer usar o que já domina e já é usado no Sistema Interno V2 (MySQL + MySQL Workbench), já que o sistema vai crescer de verdade. A objeção original ao MySQL (complexidade de instalar/gerenciar) não se aplica de fato: quem instala e mantém o MySQL Server é sempre o próprio usuário (dev), numa única máquina — a usuária final nunca encosta nisso.

Modelo de entrega: analisadas as 3 opções lado a lado.
1. `.exe` único (`--onefile`): descartado — já testado e abandonado antes (ver linha do tempo 01/09/2026, 21:13), porque extrai tudo pra uma pasta temporária a cada abertura, gerando atraso perceptível toda vez, sem correção possível.
2. Pasta com `.exe` dentro (`--onedir`): é a arquitetura já validada ponta a ponta hoje — abre rápido, sem atraso de extração.
3. Instalador completo (ex: Inno Setup) com atalho: dá a experiência mais "profissional", mas acrescenta uma ferramenta nova ao processo e mais um passo em toda atualização (gerar `.exe` + gerar instalador + rodar instalador na máquina) — sem ganho real, já que existe 1 máquina só e quem instala/atualiza é sempre o próprio usuário, presencialmente.

Escolhida a opção 2, com um ajuste que resolve o único ponto fraco dela sem custo nenhum: um atalho normal do Windows na área de trabalho da usuária, apontando pro `.exe` dentro da pasta — mesma experiência de "um ícone, um clique" de um instalador, sem ferramenta nova nem passo extra de atualização.

Operação do MySQL, definida junto: o MySQL Server é instalado uma única vez, na mesma máquina que roda o `.exe`, no setup inicial (o usuário confirmou que não tem problema precisar ir lá pessoalmente essa vez). A criação do banco (schema) em si também fica manual, feita pelo usuário no MySQL Workbench nesse mesmo setup inicial — decisão explícita dele, não automatizada. Já as migrations do Django, a cada atualização, continuam 100% automáticas: o `launcher.py` chama `migrate` sozinho toda vez que o app abre (mesmo padrão já planejado desde o bug de empacotamento encontrado em 03/09/2026, agora valendo pro MySQL igual valeria pro SQLite). Regra do usuário, fixada como inegociável: depois desse setup inicial, a usuária final nunca mais pode precisar do dev pra iniciar o servidor ou qualquer coisa do tipo — só abrir o atalho e usar.

## Decisão

- **Banco de dados: MySQL + MySQL Workbench**, no mesmo padrão do Sistema Interno V2 — substitui o SQLite decidido em 01/09/2026. Motivo: o projeto vai crescer de verdade, e o usuário prefere reusar o que já domina a resolver problema novo.
- **MySQL Server instalado uma única vez**, na mesma máquina que roda o `.exe` (conexão via `localhost`) — feito pelo usuário, presencialmente, no setup inicial daquela máquina.
- **Criação do banco (schema) é manual**, feita pelo usuário via MySQL Workbench, também só no setup inicial — decisão explícita, não automatizada.
- **Migrations são automáticas em toda atualização**: `launcher.py` roda `migrate` sozinho a cada abertura do app, sem intervenção manual — vale pro MySQL igual valeria pro SQLite, ainda não implementado no código.
- **Modelo de entrega: pasta com `.exe` dentro (`--onedir`) + atalho do Windows** apontando pra dentro da pasta — descartado tanto o `.exe` único (`--onefile`, já provou ter atraso de extração sem correção) quanto um instalador completo (complexidade e atrito de atualização desnecessários pra 1 máquina só).
- **Regra fixada**: fora do setup inicial (que pode exigir presença do dev), a usuária final nunca precisa do dev pra uso do dia a dia — só abrir o atalho.
- **Correção (04/09/2026)**: esta decisão foi escrita pensando em **1 banco MySQL só** — errado. Ainda em 04/09/2026, na mesma sessão (depois desta nota), ficou confirmado que a Devolução lida com as mesmas 2 empresas do Sistema Interno V2 (Magazine e Samvale) e precisa dos mesmos **2 bancos**, no mesmo padrão de troca de empresa — ver [[Sistema de Devoluções e Sistema Interno V2 — Mesma Empresa, Times Diferentes (Escritório e Barracão), Separação Hoje é Só de Rede]]. Isso muda o escopo da implementação: não é só configurar `DATABASES` com 2 bancos, é replicar o mecanismo inteiro do Sistema Interno V2 — `core/empresa.py` (estado da empresa ativa em thread-local), `EmpresaMiddleware` (decide a empresa ativa a cada requisição) e `EmpresaRouter` (`DATABASE_ROUTERS`, direciona leitura/escrita pro banco certo).
- **Mecanismo de troca de empresa, resolvido na prática (05/09/2026, 01:27)**: mantida a troca por sessão, igual ao Sistema Interno V2 — implementada como seletor real na navegação (não um mecanismo provisório) e testada com sucesso via `python launcher.py`. A pergunta original (sessão continua servindo pensando em PC+celular?) segue tecnicamente válida — sessão via cookie funciona em qualquer navegador, incluindo celular — mas como o seletor se comporta numa tela pequena ainda não foi avaliado; isso fica dentro da auditoria mobile-first ainda pendente (ver [[Sistema de Relatório de Devoluções — Contexto e Objetivo Inicial]], seção "Em aberto"), não é mais parte desta decisão.
- **Nomes dos 2 bancos confirmados (04/09/2026, 22:33)**: `sistema_devolucao_magazine` e `sistema_devolucao_samvale` — minúsculo, sem acento, mesmo padrão de nomenclatura do Sistema Interno V2 (`sistema_interno_magazine`/`sistema_interno_samvale`). Fisicamente separados dos bancos do Sistema Interno V2 (máquina diferente, sem rede em comum) — só espelham o padrão, não compartilham dado nenhum.
- **Driver de conexão decidido (04/09/2026, 22:33): `mysqlclient`, não `PyMySQL`** — o usuário optou por manter o mesmo driver do Sistema Interno V2 nos 2 sistemas, mesmo ciente do risco levantado (nunca testado dentro de um `.exe` PyInstaller), pra não ter 2 formas diferentes de resolver o mesmo problema. Risco real, não descartado: `mysqlclient` é extensão C — o PyInstaller pode não empacotar corretamente os binários/DLLs que ela depende, e isso só se confirma testando de verdade. **Por isso vira o primeiro item a validar**, antes de investir em models/persistência: testar uma conexão MySQL via `mysqlclient` dentro do `.exe` empacotado, com um teste mínimo.
- **Padrão de conexão confirmado (04/09/2026, 22:33)**: mesmo formato de `.env` do Sistema Interno V2 (`DB_USER`, `DB_PASSWORD`, `DB_HOST` com padrão `localhost`, `DB_PORT` com padrão `3306`). Valores reais (usuário/senha) seguem pendentes até o setup de verdade na máquina do barracão.
- **Versão do Django fixada (04/09/2026, 23:41): `6.0.6`** — ao rodar `python launcher.py` pela 1ª vez, apareceu `django.db.utils.NotSupportedError: MySQL 8.4 or later is required (found 8.0.46)`: o Django resolvido pelo intervalo original do `pyproject.toml` (`>=6.1,<7.0`) exige MySQL 8.4+, incompatível com o MySQL local (8.0.46), usado tanto pro Devolução quanto pro Sistema Interno V2 nessa máquina. Confirmado que o Sistema Interno V2 roda sem esse erro na mesma máquina, com um intervalo parecido (`>=6.0.6,<7.0.0`) — checando a versão exata resolvida lá (`poetry show django` → `6.0.6`), decidido fixar o Devolução na mesma versão exata, em vez de atualizar o MySQL local ou usar uma versão qualquer mais antiga. Resolve o conflito sem mexer no MySQL e mantém os 2 sistemas alinhados. **Ressalva**: essa fixação é pensada pro ambiente de desenvolvimento/testes atual — pode precisar ser reavaliada quando o MySQL da máquina de produção (barracão) for definido.
- **Integração testada em ambiente de desenvolvimento (04/09/2026, 23:41)**: bancos criados (`CREATE DATABASE ... utf8mb4`), `.env` real configurado (removida a variável `DB_NAME`, sem uso), arquitetura multi-empresa aplicada em código (`core/empresa.py`, `EmpresaMiddleware`, `EmpresaRouter`), `launcher.py` chamando `migrate` automaticamente pros 2 aliases. `python launcher.py` rodou com sucesso e um teste real de ponta a ponta funcionou via MySQL: cadastro de produto, nova devolução com peça parcial, PDF gerado. **Ainda sem confirmação**: `mysqlclient` dentro do `.exe` empacotado (continua sendo o item de maior risco do projeto) e teste real de troca de empresa/alias `samvale` — o teste acima rodou só com a empresa padrão (Magazine).
- **`mysqlclient` validado dentro do `.exe` empacotado (05/09/2026, 00:32)** — a maior pendência desta decisão, resolvida. O primeiro build (`--collect-submodules=core`, pra tentar empacotar `core/middleware.py`/`core/database_router.py`) não funcionou silenciosamente — sem erro, sem aviso, o pacote `core` simplesmente nunca aparecia no log de análise. Corrigido consultando a documentação oficial do PyInstaller: módulo só referenciado por string (caso do `MIDDLEWARE`/`DATABASE_ROUTERS` do Django) precisa de `--hidden-import` explícito, não `--collect-submodules`. Trocado pra `--hidden-import=core.middleware`/`--hidden-import=core.database_router`, validado primeiro num build de diagnóstico (`--debug=imports`) e depois no build final de verdade (com `--noconsole`) — testado de ponta a ponta pelo usuário: cadastro de produto, peças e PDF, tudo funcionando dentro do `.exe`. De brinde, isso também confirmou os 2 bugs de empacotamento de 03/09/2026 (`reportlab.graphics.barcode`, `django.core.management.commands`), nunca testados até então.
- **Troca de empresa e alias `samvale` validados de ponta a ponta (05/09/2026, 01:27)** — a última pendência real desta decisão, resolvida. Faltava a peça que nunca tinha sido construída: nada escrevia `empresa_ativa` na sessão, então o `EmpresaMiddleware`/`EmpresaRouter` (aplicados desde 04/09/2026) sempre caíam no padrão (Magazine). Implementado como peça real, não descartável: `core/context_processors.py` (expõe a empresa ativa pra qualquer template), view/URL `trocar_empresa` (grava a escolha na sessão e redireciona de volta) e um seletor na navegação das 3 telas. Testado via `python launcher.py`: cada empresa mostrando só o próprio catálogo (SAMVALE: "Cadeira Transferência Supermedy"; MAGAZINE: "Pulverizador a Bateria e Manual SS-20B"), sem vazamento entre os 2 bancos, nas 2 direções.
